# {metadata.title}

After months of daily Claude Code use, at work and on side projects, the thing that moved the needle was not using it more. It was the setup around it.

Four practices made the difference for me:

1. [Be specific](#1-be-specific-use-rich-input): give it rich, precise input
2. [`CLAUDE.md`](#2-master-claudemd-files): teach it your codebase once
3. [Plan Mode](#3-use-plan-mode): let it think before it writes
4. [Context management](#4-break-it-down-manage-context): keep conversations short and on topic

## 1. Be Specific (Use Rich Input)

The less specific you are, the more room the model has to make assumptions, and they rarely match what you had in mind.

### Example

<CodeBlock language="markdown" wrapLines={true} code={`
❌ Bad: "Build a portfolio website."

✅ Good: "Build me a responsive portfolio website using React 19 and Tailwind CSS v4, with a homepage, about page, and contact form. Minimal, accessible, with a focus on typography and whitespace."`} />

Name the technology, the versions, and the outcome you expect. Say what it should look like and how it should behave.

### Richer input than text

Depending on the task, add:

- **Screenshots**: drag and drop, or paste with <kbd>Cmd</kbd>+<kbd>V</kbd> (<kbd>Ctrl</kbd>+<kbd>V</kbd> on Windows and Linux). Designs, error states, UI you want fixed
- **File references**: [`@filename`](https://code.claude.com/docs/en/common-workflows#reference-files-and-directories) puts the file in context, with tab completion
- **Data**: [pipe it in](https://code.claude.com/docs/en/headless#streaming-json-input): `cat error.log | claude`
- **URLs**: the docs for the library or API you want used

Since I started working this way, I went from three or four iterations per feature to usually getting it right the first time.

Specific prompts are necessary, but explaining your stack every session gets old. That's what `CLAUDE.md` is for.

## 2. Master `CLAUDE.md` Files

Before I used `CLAUDE.md`, I was explaining our codebase setup and structure <i className="font-serif">every single session.</i>

### How it works

`CLAUDE.md` files are [loaded hierarchically](https://code.claude.com/docs/en/memory):
1. **Enterprise policy**: `/Library/Application Support/ClaudeCode/CLAUDE.md` (macOS), or `C:\ProgramData\ClaudeCode\CLAUDE.md` (Windows) - organization-wide instructions
2. **Project memory**: `/CLAUDE.md` or `/.claude/CLAUDE.md` - team-shared instructions for the project
3. **User memory**: `~/.claude/CLAUDE.md` - personal preferences for all projects

Subdirectories can carry their own (`frontend/CLAUDE.md`, `backend/CLAUDE.md`), and any of them can pull in other files with `@path/to/file`. A new session loads whichever apply to the directory you started in.

### What to include - An example

<CodeBlock wrapLines={true} collapsible={true} language="markdown" code={`
# Project: Personal Website

## Architecture
  - Next.js 15 app router with TypeScript
  - MDX for blog content

## Tech Stack
  - Framework: Next.js 15, React 19, TypeScript
  - Styling: Tailwind CSS v4
  - Content: MDX with custom components
  - Deployment: Vercel

## Commands
  - \`npm run dev\` - Start development server
  - \`npm run build\` - Build for production
  - \`npm run start\` - Start production server
  - \`npm run lint\` - Run ESLint

  ## Code Conventions
  See @.claude/code-conventions.md for detailed guidelines:
  - TypeScript strict mode, avoid \`any\` types
  - Functional components with hooks
  - Server components by default, client components only when needed
  - Semantic HTML and accessibility-first approach
  - Use \`<BlogImage>\` for images, \`<CodeBlock>\` for code examples
  - MDX layout wrapper required for all blog posts

  ## File Organization
  See @.claude/file-organization.md for structure details:
  - Components: \`/components/[ComponentName].tsx\`
  - Blog posts: \`/app/blog/[slug]/page.mdx\`
  - Utilities: \`/lib/[domain]/[utilName].ts\`
  - Types: Co-located with implementation

  ## Quality Guidelines
  See @.claude/quality-guidelines.md for:
  - Accessibility requirements (WCAG 2.1 AA)
  - Performance budgets
  - SEO best practices
  - Code review checklist

  ## Testing Strategy
  See @.claude/testing.md for:
  - Unit testing approach (if applicable)
  - E2E testing patterns
  - Accessibility testing requirements

  ## Important Rules
  - NEVER commit environment variables or secrets
  - ALWAYS test responsive behavior on mobile/tablet/desktop
  - ALWAYS ensure proper semantic HTML for accessibility
  - Blog post metadata must include title and date
  - Images must have alt text and proper optimization
`} />

### Best practices

1. **Keep it under 100 lines** - Claude loads this every session, and bloat kills signal
2. **Test and refine** - Like production prompts, test effectiveness and remove fluff
3. **Edit it from inside a session** - [`/memory`](https://code.claude.com/docs/en/memory) opens the loaded memory files, so a lesson goes in the moment you learn it
4. **Version control project files** - Check them into git for team collaboration
5. **Create multiple `CLAUDE.md` files** - Root + subdirectory (`frontend/CLAUDE.md`, `backend/CLAUDE.md`) for focused guidance
6. **Initialize with `/init`** - Claude can generate a starter `CLAUDE.md` for your project

## 3. Use Plan Mode

On simple changes like "add a loading spinner while the user data is pending", I'll start straight in `⏵⏵ accept edits on` mode.

For anything touching multiple files or with side effects, I start in `⏸ plan mode on`.

In plan mode, Claude reads and thinks before it writes. It weighs approaches, flags problems, and commits to one strategy before touching a file.

### How to enter Plan Mode
- Press **Shift+Tab** until the status line reads [plan mode](https://code.claude.com/docs/en/common-workflows#how-to-use-plan-mode)
- Or say "plan this first" in the request

### Give it room to think

Extended thinking is a toggle, **Option+T** on macOS and **Alt+T** elsewhere, and [`/effort`](https://code.claude.com/docs/en/interactive-mode) sets how hard the model works on each turn. I keep thinking on in plan mode and raise the effort for:

- Unclear requirements that need exploring first
- Multi-file refactors and architectural changes
- Anything security-sensitive

Then ask a question that deserves the extra thought:

<CodeBlock wrapLines={true} language="markdown" code={`
"Plan real-time collaboration for our React app. Compare WebSockets,
Server-Sent Events and polling, cover database requirements, conflict
resolution, and what changes at 10k concurrent users."
`} />


### Store Plans as Files

For bigger features, have Claude write the plan to a file:
<CodeBlock wrapLines={true} language="markdown" code={`
"plan the implementation of a role-based access control system and output
the plan to /docs/role-based-access-control-plan.md. Include:
- Overview of roles and permissions
- Required database schema changes
- API endpoint modifications
- Frontend UI updates
- Testing strategy"
`} />

Now you have something to review before any code exists. Adjust the approach, add constraints, cut scope, all without spending tokens on implementation. Once agreed, the file stays the reference for the whole feature, across as many `/clear`s as it takes.

## 4. Break It Down & Manage Context

The context window is [200k tokens](https://code.claude.com/docs/en/context-window) by default, with 1M opt-in on the newest models. That sounds like plenty until you're deep in a debugging session and the answers get vaguer about your setup with every turn.

### The problem with context pollution
- [Auto-compact](https://code.claude.com/docs/en/costs#reduce-token-usage) spends tokens summarising the conversation, and loses detail doing it
- Error logs, permission prompts and repeated output pile up
- Large [MCP](https://code.claude.com/docs/en/mcp) results, a whole page fetch or a big query, land in context and stay there
- Long conversations drift toward generic answers

### Best practices for context management

1. **Use [`/clear`](https://code.claude.com/docs/en/sessions) frequently**

  I clear after every finished subtask. Once the code is committed and the tests pass, that context has done its job.

2. **Break large tasks into phases**

  <CodeBlock language="markdown" wrapLines={true} code={`
  Phase 1: "Review the authentication system and identify all endpoints"
  [Review results, then clear]

  Phase 2: "Add rate limiting to the login endpoint at /api/auth/login"
  [Implement, test, commit, then clear]

  Phase 3: "Add rate limiting to remaining auth endpoints..."
  `} />

3. **Be surgical with file references**

  - Instead of: "Look at everything in the `/components` folder"
  - Try: "Review `@components/AuthForm.tsx` and `@hooks/useAuth.ts`"

4. **Let Claude write the breakdown**

<CodeBlock language="markdown" wrapLines={true} code={`
"Generate a checklist of all files that need updating to migrate from
Redux to Zustand. For each file, describe the required changes."
`} />


5. **Turn the breakdown into tickets**

Then take each one in its own conversation.

<CodeBlock language="markdown" code={`
"Generate 5 GitHub issues for this migration. Use the gh CLI to create them
with proper labels and link them to the epic."
`} />

### The guiding principle

Keep the context window full of things that matter to the task in front of you, and nothing else.
